⚡ Automatizaciones — Flows vs. Apex Triggers
Record-Triggered Flow · Screen Flow · Scheduled Flow · Apex Trigger · ¿Cuándo usar cada uno?
💡Salesforce sigue el principio "Clicks before Code": preferir Flow sobre Apex cuando sea posible. Sin embargo, la elección depende de la complejidad de la lógica, los volúmenes de datos y cómo el equipo implementa automatizaciones en cada proyecto.
🔄 ¿Flow o Trigger? — Árbol de decisión
👨‍💻
¿Puede un admin configurarlo sin código?
→ Flow
⚡
¿Requiere lógica compleja, bulkification o integración síncrona?
→ Considerar Apex
📋
¿Lo define el estándar del proyecto o la empresa?
→ Seguir el estándar
⚠️ Nota de consultor: En proyectos reales, la decisión Flow vs Trigger muchas veces ya está tomada por el estándar del cliente o del equipo técnico. Algunos equipos mantienen toda la lógica de negocio en Apex para mayor control y testabilidad; otros prefieren Flow para mantener el acceso al admin. Siempre validar antes de empezar a implementar.
🌍 Tipos de Flow
TipoCuándo se ejecutaInteracción usuarioCaso de uso típico
Record-Triggered Al crear / actualizar / eliminar un registro No Actualizar campos, notificar, crear registros hijos al guardar una Oportunidad
Screen Flow Lanzado por usuario (botón, Quick Action, Lightning App Page) Sí — pantallas Wizard guiado para convertir Lead, formulario de alta de cliente
Scheduled (Time-based) En horario o fecha programada No Enviar recordatorio 7 días antes del vencimiento de un contrato
Autolaunched (no trigger) Invocado desde otro Flow, Apex o Process Builder No Sub-flow reutilizable de lógica de negocio
Platform Event-Triggered Al recibir un Platform Event No Reaccionar a eventos publicados desde integraciones externas
⚠️Process Builder y Workflow Rules están en modo "No New Enhancements" (deprecados funcionalmente). Salesforce recomienda migrar a Flow. En proyectos legacy aún los encontrarás activos.
⚡ Record-Triggered Flow — Detalle de configuración
Momento de ejecución
Before Save
Se ejecuta antes de que el registro se guarde en la BD. Solo puede actualizar campos del mismo registro. No puede crear otros registros ni enviar emails. Más eficiente (sin DML extra).
After Save
Se ejecuta después de guardado. Puede crear registros relacionados, enviar emails, llamar a subflows, hacer callouts (async). Accede al registro antes y después del cambio.
Optimized for / Fast Field Updates
Fast Field Update (Before Save)
Actualiza campos del mismo registro sin DML. Similar a un Before Trigger de Apex. Es la opción más performante para cálculos de campos.
Actions and Related Records (After Save)
Actualiza registros relacionados, crea hijos, lanza subflows, manda notificaciones. Usa DML, por lo que cuenta contra governor limits.
💡Ejemplo Genie Trips: Al cerrar una Oportunidad como Ganada → Before Save calcula el campo "Comisión__c". → After Save crea los registros Ticket__c y publica el post en Chatter.

🚫 Governor Limits — Los más críticos
⚠️Los Governor Limits son límites por transacción que aplican tanto a Flows como a Apex. Superarlos genera un error de runtime que hace rollback de toda la transacción.
LímiteValorAplica a
SOQL queries100 por transacciónFlow + Apex
Registros por SOQL query50.000Flow + Apex
DML statements150 por transacciónFlow + Apex
Registros por DML operation10.000Flow + Apex
Callouts HTTP100 por transacciónApex
CPU time10.000 msFlow + Apex
💡 En cargas masivas (Data Loader), cada batch comparte los límites. Un Flow mal diseñado con SOQL dentro de un loop puede causar "Too many SOQL queries: 101".
📋 Cuándo usar cada herramienta — Guía rápida
✅ Usa Record-Triggered Flow (Before Save) cuando:
Necesitas actualizar un campo del mismo registro al guardar (ej: calcular descuento, setear fecha, concatenar nombre).
✅ Usa Record-Triggered Flow (After Save) cuando:
Necesitas crear registros hijos, notificar, publicar en Chatter, o llamar un subflow al guardar.
✅ Usa Screen Flow cuando:
El usuario necesita un asistente paso a paso (wizard) para completar una acción compleja.
✅ Usa Apex Trigger cuando:
La lógica requiere manejo de grandes volúmenes (bulkification), lógica cross-object compleja, callouts síncronos, o integración con sistemas externos en tiempo real.
⚠ Evita combinar ambos sin coordinación:
Un Flow After Save que dispara un Trigger que vuelve a actualizar el registro puede causar recursión o superar governor limits. Definir un estándar en el proyecto.

🔄 Order of Execution — Ciclo de una Transacción
¿Qué ocurre exactamente cuando hago clic en "Guardar"?
💡Entender el Order of Execution es fundamental para diagnosticar comportamientos inesperados, evitar recursión y optimizar el rendimiento. Todo ocurre en una sola transacción de base de datos — si algo falla, se hace rollback de todo.
🔄 Orden completo de ejecución — Record Save
1
El registro entra al sistema
El usuario o API envía el registro. Salesforce carga los valores existentes de la base de datos (si es una actualización).
2
System Validation
Verifica reglas del sistema: campos requeridos por página layout, tipo de dato correcto, formato de campos únicos, integridad referencial (lookup/MD). Independiente de las Validation Rules del admin.
3
Before-Save Flows (Record-Triggered)
Se ejecutan los Flows configurados como Before Save. Pueden modificar campos del mismo registro sin DML. Se ejecutan en orden de "Last Modified Date" si hay varios.
4
Apex Before Triggers
Lógica Apex marcada como before insert / before update / before delete. Puede modificar campos del registro en memoria antes de guardarlo. Ideal para validaciones y derivaciones complejas.
5
Validation Rules (Admin)
Se evalúan las reglas de validación configuradas por el administrador. Si alguna falla, se muestra el error al usuario y la transacción se detiene aquí (no llega al After). No aplican en ciertos contextos (SOAP API con allOrNone=false, etc.).
6
Duplicate Rules
Salesforce evalúa las Duplicate Rules. Si está configurada como "Block", la transacción se detiene. Si es "Alert", continúa pero notifica.
7
▣ COMMIT a la base de datos
El registro se escribe en la base de datos. A partir de aquí se disparan los procesos After. El paso anterior (antes del commit) es el punto de no retorno para campos del registro.
8
Apex After Triggers
Se ejecutan los Apex Triggers after insert / after update / after delete / after undelete. El registro ya está en BD. Típicamente se usan para crear registros relacionados, publicar eventos o lanzar jobs asíncronos.
9
Assignment Rules
Se evalúan las reglas de asignación (Lead/Case). Se asigna el Owner según la primera regla que coincida.
10
Auto-Response Rules
Se envía el email de respuesta automática si aplica (Web-to-Lead, Email-to-Case).
11
After-Save Flows (Record-Triggered)
Flows configurados como After Save. Pueden hacer DML en otros registros. Se ejecutan después de los Triggers estándar. Pueden generar nuevas transacciones (recursión si no se controla).
12
Escalation Rules
Se evalúan las reglas de escalamiento de Casos (si el objeto es Case). Programan acciones futuras si el caso no se resuelve en N horas.
13
Roll-Up Summary Fields & Cross-Object Formulas
Salesforce recalcula los campos Roll-Up Summary en el registro padre (Master-Detail). También recalcula fórmulas cross-object que referencian este registro.
14
✅ Commit final + respuesta al usuario
La transacción completa se confirma. El usuario ve el registro guardado. Los procesos asíncronos (Queueable, Future, Batch) se encolan para ejecutar fuera de la transacción principal.
💡 Puntos clave para el consultor
⚠ Validation Rules NO aplican en Before Triggers
Los Apex Before Triggers se ejecutan ANTES que las Validation Rules. Un trigger puede hacer bypass de una validación si setea el valor incorrecto. Hay que tener cuidado al diseñar la secuencia.
⚠ Todo es una sola transacción (hasta los After Saves)
Si un After-Save Flow falla, toda la transacción hace rollback, incluyendo el guardado original del registro. El usuario verá un error.
🔄 El orden entre múltiples Flows del mismo tipo
Cuando hay varios Record-Triggered Flows para el mismo objeto/evento, Salesforce los ejecuta según la fecha de modificación (más reciente primero en algunos casos). Para mayor control, combinarlos en un solo Flow o usar un Apex Trigger.
💾 Async se escapa de la transacción
@future, Queueable, Batch y Platform Events-triggered se ejecutan en una NUEVA transacción. Tienen sus propios governor limits y no hacen rollback si la transacción original falla.

📋 External ID vs. Record ID
Record ID: generado por Salesforce, 15 o 18 caracteres. El de 18 es case-insensitive y recomendado para integraciones. No cambia nunca.
External ID: campo marcado como ID externo (Text/Number/Email). Permite relacionar registros con sistemas externos (ERP, SAP). Se usa en Upsert para evitar duplicados. Máx. 25 por objeto.
🚫 Gestión de Duplicados — Matching Rules & Duplicate Rules
💡Las Matching Rules definen cómo identificar duplicados (por Email, Nombre, Teléfono…). Las Duplicate Rules definen la acción: Permitir (con alerta), Bloquear, o Solo reportar. Disponibles para Leads, Contactos, Cuentas y objetos custom.
